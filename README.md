# 《魔法少女的魔女审判》AI 游玩包

> **这是什么**：一套「让 AI 自己玩一款推理游戏」的静态化流程。把游戏按场景与分支拆成 1900+ 个中性编号的小文件，配一份主持人用的路线索引；游玩 AI 只读文本（图片用 read_image），每收到一份就写一份「逐句体验 + 感想 +（有决策时）决策」的独立文档，另维护一份跨上下文压缩的 Memory.md。
>
> **本仓库只放流程**：构建脚本、提取脚本、给 AI 的提示词、说明文档和 samples/ 里的三份效果样本。**不含任何游戏文本、图片或音频**——所有游玩内容都需要用你自己购买的正版游戏在本地生成。素材来源与授权见 CREDITS.md，脚本许可见 LICENSE。
>
> **效果样本**：samples/（原文引用已省略为「第 N 句」）。**剧透警告**。

这是一个供个人游玩的静态 Markdown 包。原文来源于 Manosaba Library，构建时固定记录上游提交；请勿重新发布生成的游戏全文或素材。

当前成品基于上游提交 `ca27afbed17fb9a957d9af1117f06288d5a52451`，包含一周目 5 章、二周目 6 章。生成结果共有 1993 个 Markdown、33295 条源对白、33908 个对白实例（33231 个唯一标签）和 483 张图片；构建器确认所有源对白均已覆盖。

## 目录

- `游戏包/`：只放玩家可以看到的内容，按周目、章节、正文、魔女审判和素材分层。
- `主持人/路线索引.json`：主持人根据 AI 的决定查找下一份文件；`证物栏` 按章节登记审判时要发送的证物清单，`魔女图鉴` 按章节登记手机 APP 快照（`场景-NNN-图鉴.md`），`事件插画` 按章节登记审判收尾「再現」演出的插图快照（`事件插画.md`），`结局插画` 登记片尾插图（`结局插画/结局插画.md`）；`关键字` 按文件登记魔女审判台词里可点击的词（词面、所在台词与说话人、点了会落到哪个决策文件的哪个选项）；`清单` 按决策文件登记证物/人物档案清单阶段的选项（名称、哪一件对、回应文件）——`清单` 是**主持人侧**的答案表，绝不能发给游玩 AI；这几项都可单独补发。不得发给游玩 AI。
- `主持人/构建报告.json`：本次构建的来源提交、数量统计与警告。
- `AI开场白.md`：首次游玩前发送给 AI 的规则和回复格式。
- `tools/extract-local-story.py`：从本机正版游戏只读提取 Naninovel 演出时间轴。
- `tools/build.mjs`：使用 Node.js 标准库实现的可重复构建脚本。

## 构建

需要 Node.js 18+、Git、Python 3 和 UnityPy。首次准备依赖并从正版游戏提取时间轴：

```powershell
python -m pip install --target .cache\unitypy UnityPy
$env:PYTHONPATH = "$PWD\.cache\unitypy"
python tools\extract-local-story.py 'D:\steam\steamapps\common\manosaba_game\manosaba_Data\StreamingAssets\aa\StandaloneWindows64' '.cache\local-story'
```

提取器除了分章时间轴，还会写出 `witchbook.json`（魔女图鉴条目文本，按版本）和 `witchbook-initial.json`（开局就装在手机里的条目），构建时用来还原手机 APP 的解锁时机。

随后构建游玩包：

```powershell
node tools/build.mjs
```

脚本优先读取环境变量 `MANOSABA_SOURCE`，否则读取本机临时缓存；缓存不存在时会从公开仓库浅克隆。演出时间轴优先读取 `MANOSABA_STORY` 指定的目录，否则读取 `.cache/local-story`。生成内容位于 `游戏包/`，主持人路由位于 `主持人/`。脚本只重建这两个由它管理的目录，正版游戏目录始终只读。

每次构建都会检查路由目标、图片引用、玩家可见名称、对白覆盖、决策是否可以离开、可达文件能否走到结局、每一章正文是否可达，以及两个周目能否从起点抵达终点。详细统计见 `主持人/构建报告.json`；`unreachableFiles` 会列出所有不会由路线送达的文件。

## 主持方法

1. 先把 `AI开场白.md` 发给游玩 AI。
2. 在 `主持人/路线索引.json` 查找 `起点`，发送对应文件。
3. AI 没有遇到选择时，按该文件路由的 `继续` 发送下一份。
4. AI 做出选择时，按 `选项` 中对应字母发送下一份。魔女审判的选择是“点台词里的关键字”，AI 会在决策里写明点了哪个词；对不上号时用 `路线索引.json` 的 `关键字` 字段核对。
5. 证物现在按游戏里的解锁时机直接插在正文/审判文件里（见下），正常流程不用额外发；`证物栏` 里该章的文件改成**按需参考**——想查已解锁的证物清单时再发，不要提前整章发（19 条多版本文案会轻微剧透）。
6. 某个场景已经读过、之后才补上手机 APP 内容时，直接发该场景的 `-图鉴.md` 快照（见 `路线索引.json` 的 `魔女图鉴`），不要重发整场；想单独补发某章的「事件插画」时用同表的 `事件插画` 快照，结局后补发片尾插图用 `结局插画`。
7. 游玩 AI 必须使用声明了图像输入的模型，例如 `deepseek-v4-flash-vision-exp`；默认的 `deepseek-v4-flash` 不接受图片，游玩 AI 只会按约定如实写“这一处我没有看到画面”。人设照旧可以带着：称呼、口癖和“等你发下一份”都无妨，约定只要求它们留在文档外——文档本体仍然只有逐句体验（文末有选择时再加决策）。
8. 游玩 AI 会把体验文档写成独立文件（默认 `体验-场景-NNN.md`，审判篇 `体验-审判-NNN.md`），主持人把它收进 `record/`；对话区只用来闲聊。
9. 不要把 `主持人/`、`tools/` 或未抵达的文件交给游玩 AI。游玩 AI 也不得改动 `游戏包/` 里的文件；万一被写过，重新构建一次即可复原。

玩家目录和主持人索引物理分离，玩家可见文件只使用中性编号。每章都有独立的 `正文/`、`魔女审判/` 和 `素材/`。

普通选择截断在真正做决定的那一句：正文在这里以 `请选择` 收尾，选后剧情另存为 `场景-NNN-后续.md`；指向 Bad 结局的选项直接送进对应的正文文件。魔女审判同理，用 `回应`/`决策` 文件分叉。

魔女审判的选项不是菜单：游戏里要用手点掉台词里可疑的词。构建时按脚本的 `<link="Objection_…">` 标记把这些词就地圈成 `〔词〕`，并在那一句下面加一行 `> 🔍 可点击关键字：**词** → 审判-0NN-决策-0M.md 选项 X`；决策文件里每个选项后面也标明要点哪个词（普通按钮选项写「普通选项（不是关键字）」），并在 `## 机制` 里说明这一阶段是点词还是选字母。同一段台词里可能同时圈出好几个关键字，点哪一个由玩家决定。全包共 595 个关键字点位、681 条索引记录，落在 145 个审判文件里。

证物 / 人物档案的选择另算一类（脚本 `ChoiceEvidence` + 唯一的 `CorrectEvidenceId`）：游戏会弹出你手上的清单，只有一件是对的，挑错就是驳回 + 掉血 + 退回上一层重选。库数据把那段「通用驳回」对白也记成了正确那件的同名分支，构建时会把同名却不对的那条改标成 `（其他证物）`／`（其他人物档案）`（另有 18 条库里名字本来就是「无」的失败分支同样处理），这类阶段的 `## 机制` 会说明是「弹清单挑一件」。全包共 78 个证物/人物档案选择阶段。剩下 1 处同名（二周目第 02 章 `审判-024-决策-01.md` 的 B/C）是脚本里真的两个同名 choice id，保留原样并注明「同名选项，通往不同回应」。

更进一步，这类阶段的选项现在**按游戏里的解锁时机还原成「此刻手上的清单」**：提取器从脚本的 `ChoiceEvidence` 读出分类与唯一正确的 `CorrectEvidenceId`，构建时按 `@updateWitchBook` 的时间轴（节点顺序 + 行号）算出这一题时手机上已经解锁的全部证物/人物档案，直接列成选项（共 **58** 个阶段、**1478** 个选项，最多的一次 43 件，字母 A…Z 之后接 AA、AB）。清单里**不标哪一件对**，由游玩 AI 自己挑；挑错就走通用驳回 + 掉血 + 退回上一层。哪一件对只写在主持人的 `清单` 字段里；少数没法按清单出题的阶段（库里只记了失败分支，或证物选项与普通选项混在一起）也不再给任何正误标记——**玩家可见文档里不出现「正确的证物」这类字样**。

手机 APP「魔女图鉴」的四类内容都按游戏里的解锁时机插进正文（`@updateWitchBook` 事件）：**规定**、**记录**、**证物**、**人物档案**。

- 开局就装在手机里的：5 条规定 + 7 条记录 + 15 份人物档案 v1，挂在第一次提到「魔女图鉴」的那一句后面。
- 剧情解锁：证物 143 处、人物档案 125 处、记录 22 处，各插在触发那一句之后；证物第一次解锁时连图片一起给（图放在该证物所属章节的 `素材/证物/`）。
- 同一条目同一版本只发一次；版本更新只发新增的那一段，标题带“（更新）”。
- 每个插过条目的文件同时生成一份 `xxx-图鉴.md` 快照（共 111 份），内容与正文里夹带的完全相同，供主持人单独补发或复查。
- 地图（`F1/F2/B1/设计图`）不插：素材层面只有基础版，二周目的「诺亚的画室」是运行时区域变化，没有新图。

审判收尾的「再現」演出（游戏里由 `@spawn Reenact_…` 触发）也按剧本行插入：每章收尾审判节点里那一句之后，插上该演出的底图；共 56 张，落在 10 章（二周目第 5 章没有再現）。每章另出一份 `事件插画.md` 快照，内容与正文里的一致。

图片链接写的是本工作区的绝对路径，游玩 AI 可以直接用 `read_image` 打开，不需要主持人再补发；把 `游戏包/` 搬到别的路径后需要重建。

## 图片范围

图片范围包括首次正式自我介绍时的人物档案整图、分章证物，以及能由正版 Naninovel 演出时间轴精确对应正文的过场 CG。时间轴从本机正版 AssetBundle 只读提取，涵盖 `stills`、`ending`、`kari`、`cutin`、`tricks`；同一位置连续切换的图片按原作顺序全部保留，纯背景始终排除。复制到玩家目录时统一改为中性编号，避免文件名剧透。

图库“剧情 CG”共有 172 张 Stills。逐一扫描 440 个 Naninovel 脚本（正文/结局 420 个 + System、Debug 等 20 个）后：157 张由正文脚本精确定位，`Still_001_001` 只被调试脚本 `Debug_Actors` 引用，其余 14 张在任何脚本里都没有出现。这 15 张里 `Still_001_001` 和 `Still_002_001` 是游戏开屏/标题画面，正文本来就不会播放；剩下 13 张（`Still_340_002`、`Still_420_000` 与 11 张 `Still_570_*`）没有调用证据，因此没有看图猜测或强行插入，编号完整记录在 `主持人/构建报告.json`。当前共还原 410 次 Stills 演出和 27 次 Tricks 演出，合计 437 次过场演出；重复出现会保留演出次数，但同章同一素材只复制一份。另外补上了 56 张审判收尾「再現」演出的底图（见上）和 9 张片尾「结局插图」，所以图片总数是 483：256 张过场 CG + 56 张事件插画 + 9 张结局插画 + 136 张证物 + 26 张角色立绘。（证物补上了二周目第 5 章的 6 张——库里把这批的 act/chapter 标成了 0，现在按 `Clue_010_*` 的编号归回二周目第 5 章。）

「诡计」（Tricks）19 张里 18 张已按脚本位置插进正文（共 27 次演出）；剩下 `Trick_005_003_001` 在全部 440 个脚本里都没有引用，判定为未使用素材，没有插入。「结局」（Ending）10 项里，9 张 631×434 的小插图是**片尾 credits** 用的（游戏用 `EndingStill` + `EndingStills` 图集播放），正文没有任何脚本引用，所以不插剧情，单独放在 `游戏包/结局插画/` 作为参考文件；另 1 项是这些插图的 4096×4096 源图集，只是打包容器，没有单独收录。

## 已知边界

- 玩家文件共 1993 个，其中 1808 个可从两个起点抵达。`unreachableFiles` 列出的 53 个文件不会由路线送达：没能对应到审判分支的证言/证物追问阶段，其中有 219 行对白只存在于未进入的分支里。
- 清单阶段的上游数据缺口：18 个阶段库里没有记录正确答案（按失败分支列出，挑哪个都能继续，不会卡死）；6 个阶段把 Clue 选择与 Profile 选择并进了同一个 choice（不给正确标记，候选保留给玩家自己挑）；另有 1 个阶段（一周目 `审判-008-决策-05.md`）库里只记了正确项、没有失败分支，按清单出题、挑错就退回这一题重挑。
- `referenceFiles` 列出的 132 个文件（11 个分章 `证物栏.md` + 111 个 `xxx-图鉴.md` 快照 + 10 个分章 `事件插画.md` + 1 个 `结局插画/结局插画.md`）不走路线，由主持人按“主持方法”第 5、6 步按需发送。
- 表格与统计口径来自上游提交 `ca27afbed17fb9a957d9af1117f06288d5a52451`；更换上游提交后需要重建并复核 `unreachableFiles`。
- 图片链接是绝对路径，因此整个游玩包不能直接搬到别的目录；换目录后重新构建即可。
